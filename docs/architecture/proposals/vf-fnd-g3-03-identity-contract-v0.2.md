## D1 — environment, profiles and compatibility

Use configuration registry, not a runtime request issuer discovery. Example only:
- issuer https://iam.example.invalid; authorization endpoint /oauth2/authorize; token endpoint https://iam.example.invalid/oauth2/token; JWKS https://iam.example.invalid/oauth2/jwks; exact origin, TLS, pinned configured metadata, no redirect to unapproved host or token-controlled jku/x5u.
- Storage resource https://storage.example.invalid/api; human client storage-browser-t1, confidential service asset-backend-t1, tenant T1, application Storage, exact active ApplicationTarget T1-storage; human redirect https://storage.example.invalid/callback. T2 has distinct clients/bindings; issuer and audience may be shared only with explicit tenant admission, no implicit cross-tenant access. Actual client IDs server-generated globally unique; these aliases are fixture labels only.
- legacy access profile L0: current aud=client_id, no required jti; exact named legacy config only. New profile R1: typ at+jwt, iss, sub, singleton aud resource URI (string or one-element array interpreted equivalently), client_id, iat, exp, jti, scope (space-delimited string); no tenant or roles used for authority. Reject duplicate JSON keys, unexpected critical/remote key header, weak/malformed key/token, non-singleton aud, ID token or unsupported actor/delegation claim. New token max 8192 encoded characters, jti 128 ASCII visible, issuer/sub/client/aud bounded by approved model; exact strings, no normalization. Allow RS256/384/512 only configured per issuer, initial R1 RS256; keep existing signer algorithms for legacy. ID token remains aud client and existing auth_time/nonce. Service token never ID token, auth_time or human impersonation. Human subject existing opaque derivation unchanged; service opaque stable separate namespace proposed hash of version prefix + tenant + identity ID (not client ID, no change on key rotation; one initial client per subject). Consumer binding includes exact issuer/sub/aud/client_id. No profile or issuer selected from unverified token; endpoint/server config selects one profile. New profiles disabled until G4 acceptance and separately authorized activation.
- Source finding: current Storage VerifiedAccess lacks client_id; Bindings.resolve(issuer,subject,audience) and USER-only check; AccessAuthentication checks audience containment. Successor must carry verified client_id and exact single aud, route/profile config, typed actor kind and active binding; update all facade consumers, not merely verifier. Existing FS #17–19 owns this work. No new profile implementation under G3-03.

## D2b — service client authentication

Choose private_key_jwt candidate because proof-of-possession avoids distributing a shared secret, matches #546 supported provider/decoder evidence; mTLS alternative requires certificate lifecycle and infrastructure evidence; managed secret fallback not enabled. Use standard JWT library decoder with registered key and strict algorithms, no raw custom crypto; dependency/license/CVE review before code. Exact client registration selects Credential-owned active key reference; no token-controlled discovery or public client secret. Public key only, RSA >=2048, unique kid in client credential set, sign use; private key stays in client custody, never IAM ordinary APIs/events/audit/logs. Enrollment requires Administration-authorized proof of possession, independent key material and immutable versioned public key/fingerprint; reject reused kid with different material. Key rotation via Credential existing separate rotation aggregate, proposed max overlap 24h only while both effective and independently approved; compromise immediately suppresses new issue, no automatic reactivation. Actual key enrollment/custody and overlap still approval input; no stored raw private key or client secret.

Assertion: OAuth token request grant_type=client_credentials, client_id exact, client_assertion_type urn:ietf:params:oauth:client-assertion-type:jwt-bearer, client_assertion, resource exact URI and requested registered scope. iss=sub=client_id, aud exactly singleton configured token endpoint, iat/exp required, 0<exp-iat<=120s, iat<=now+30s, exp>now (no extra expiry leeway for assertion); jti unique and bounded. Verify signature, algorithm, key ownership/revision/effectiveness and all claim checks before reserve. Reject wrong audience/key/subject, expired, duplicate or malformed; same jti in different client scope isolated. Atomic durable unique (issuer identifier, tenant ID, client registration ID, SHA256(jti)); one winner across instances/restart. Scope not key ID: rotation cannot reset replay. Retain until exp+30s at minimum, delete expired rows bounded (candidate batch <=1000, at most once/minute, indexed expiry); purge clock uses DB clock and skew bound. On DB outage/uncertain commit deny; never erase reservation on downstream denial or signing failure. Rate-limit client authentication and bound assertion length <=8192 before parsing. No raw assertion, jti, token or private material in evidence. #546 tested 1/20 on disposable PG using (issuer,client,hash) and table outage; proposed tenant/registration binding and actual credential lifecycle require G3-04/05 tests, not already implemented. Race: current checks and conditional replay reserve, recheck exact registration/credential/tenant/subject/admission immediately before signing; no distributed linearizable revocation claim. Revocation commits independent of evaluator; no issue after observed revocation; previously minted JWT bounded by D3. No external calls inside authoritative transaction. Error neutral invalid_client/invalid_grant as appropriate, unavailable mandatory authority temporarily_unavailable, no leak.

## D3 — candidate security timing and trust

| Control | Candidate numerical setting |
|---|---|
| R1 access lifetime | max 300s; exp>iat, iat no more than 30s future; exp+30s max leeway, bound residual <=330s in issuer/validator aligned clock time; proposed max relative clock drift 5s (measured, stop issuing/accepting when clock health exceeds bound) -> <=335s elapsed-time JWT-only bound after issuance/revocation at issuance |
| Client assertion | max 120s, future iat tolerance 30s, exp strictly future; replay retain exp+30s minimum |
| JWKS transport | HTTPS only pinned issuer/config, 2s connect/5s total, max 256 KiB and 32 keys, no redirects, single-flight refresh |
| JWKS cache | refresh 30s; max snapshot age 60s measured on monotonic elapsed time; unknown kid one bounded refresh; failed mandatory refresh/stale/malformed -> deny, no indefinite fallback |
| Key rollover | publish replacement before issue; retain old public keys  >=335s from last issue plus 60s cache propagation (candidate 395s minimum), emergency removal hard stale <=60s after authenticated snapshot publication/removal is observable, plus measured clock/network propagation uncertainty; no stale positive fallback; no promise of instant cancellation |
| Authority | current read every new authorization, replay, transfer issue/claim and sensitive operation; no positive cached remote authority (TTL 0), no unavailable/stale fallback, bounded 2s authority query deadline candidate; revoke local grant denies new decisions after commit |
| Transfer | proposed max 60s residual from successful claim to forced termination, handle expiry min(session, token, 60s); explicit new bearer/current authority + single-use handle for new claim; no automatic resume/renewal until supported; block activation of service bytes if actual transport cannot enforce bound |

Storage current gateway only cooperative monotonic checks, blocking I/O not guaranteed; durable grant lock protects local issue/claim, remote revocation is check-time race, no in-flight cancellation. 60s cap is proposed risk target, not current behavior or promise. G4 must measure real connector/socket/provider cancellation, rate/concurrency, maximum file size/workload, uncertain effect/reconciliation and residual; if unmet, restrict initial service to metadata/initiation with no byte transfer or approve a different bounded policy before activation. No signed URL or provider access bypass. Local authority and cryptographic validity separate; new issuance denies if mandatory unavailable; old JWT not globally invalidated by logout. No online introspection initial default, high-risk policy separate.

## D4 — logical model, ownership and transaction design

Keep existing SsoClientRegistration (public OIDC scopes OPENID/PROFILE/EMAIL only) compatible; propose typed successor extension rather than replace/overload old enum. Catalog tenant-owned ClientRegistration references exactly one tenant-local admitted ApplicationTarget; kind PUBLIC_HUMAN / CONFIDENTIAL_HUMAN / CONFIDENTIAL_SERVICE, globally unique immutable client_id, revision, status DRAFT/ACTIVE/SUSPENDED/RETIRED, explicit grant modes and exact redirect for human; no redirects for service. ResourceRegistration stable id + exact immutable audience URI, explicit Tenant owner or separate deployment-owned shared offering + explicit Tenant admission per ADR-0049, allowed protocol scope identifiers and revision. ClientResourceBinding tenant-owned (client, resource, exact ApplicationTarget, grant kinds, exact scoped permissions, revision, state). Unique active pair per tenant/client/resource, FK within tenant where same owner; deployment offering via explicit admission, no nullable ownership. Resource/target/client suspension immediately denies issuance, terminal retirement triggers Access-owned durable reduction; Catalog never mutates AccessAssignment. No generic CRUD/JSON model. ADR-0063's existing Credential kinds are metadata and no general CredentialBinding is approved; the exact typed service authenticator extension and any scoped ADR-0063 amendment must be reviewed under G3-04 before implementation.

Identity owns SERVICE/WORKLOAD and Principal plus accountable owner relationship; initial service client has explicit one tenant + one nonhuman Identity + one eligible Principal + allowed Credential binding. Catalog records stable subject/Principal references in service binding; Credential owns authenticator keys, effectiveness/revision and rotation; separate semantic query returns exact eligible credential proof. No cross-capability DB write, no duplicate user/account/key authority. Current Principal/Identity/tenant/target/app admission and governed Access query required for service grant, not only scope. Access/Governance authorize admitted assignment and reduction; use revision/causal idempotency, semantic commands and curated facts; Audit data-minimized evidence correlated to operation. Administration governs registration/activation/key management separately from business access. Platform owns protocol code/session/assertion replay technical state; no replay table authority over Credential. Proposed operations (not API paths): RegisterClient/BindResource/BindServiceSubject/Activate/Suspend/Retire, Enroll/Rotate/RevokeCredential, Grant/RevokeApplicationAccess; optimistic revisions, causal idempotency for enrollment/activation, bounded transaction per owning aggregate, external calls after commit. Service subject cannot change silently; successor registration if identity changes. Use V42 legitimate additive migration only after G3-04 approval, preserve legacy records and code semantics; exact schema keys/indexes/constraints and retention reviewed by Data; no DDL now.

Storage owns binding (iss,sub,aud,client_id)->local actor, tenant, consumer, allowed action and grant-kind; user/service explicit type, no SYSTEM public token, no cross-tenant inference. Existing SecuredFiles uses exact tenant/purpose/file grants and USER-only; service must be explicitly enabled on narrow operations, not blanket bypass. Proposed scopes are protocol ceilings, not actual file grants:
- files.read: READ_METADATA, READ_SESSION (only if owned/exact grant); DOWNLOAD_TRANSFER separate explicit grant and G4 transfer bound; LIST_METADATA requires separate files.list (not initial service).
- files.write: INITIATE and UPLOAD_TRANSFER (distinct local grants, exact purpose and session; transfer gated by D3); no implied read, policy/admin, purge/delete/restore, signed URL, arbitrary cross-app access. For first reference service propose one fixture purpose asset-attachment, exact initiating consumer asset-backend, owned file/session only; actual Product/Storage purpose names and grant issuance/revocation owner unconfirmed. For human exact file/read and purpose grants per existing rules; no automatic tenant-admin bypass.
- Require current membership/module entitlement + allowed client/action + local purpose/file grant for every operation/replay; grant revocation denies, no privilege from JWT scope/claims. Storage authoritative Grants port currently fixture/implementation slices; actual source #19 and local grant administration policy need explicit owner approval. No service user impersonation, delegated user workflow deferred.
