## D2b — service client authentication

Choose private_key_jwt candidate because proof-of-possession avoids distributing a shared secret, matches #546 supported provider/decoder evidence; mTLS alternative requires certificate lifecycle and infrastructure evidence; managed secret fallback not enabled. Use standard JWT library decoder with registered key and strict algorithms, no raw custom crypto; dependency/license/CVE review before code. Exact client registration selects Credential-owned active key reference; no token-controlled discovery or public client secret. Public key only, RSA >=2048, unique kid in client credential set, sign use; private key stays in client custody, never IAM ordinary APIs/events/audit/logs. Enrollment requires Administration-authorized proof of possession, independent key material and immutable versioned public key/fingerprint; reject reused kid with different material. Key rotation via Credential existing separate rotation aggregate, proposed max overlap 24h only while both effective and independently approved; compromise immediately suppresses new issue, no automatic reactivation. Actual key enrollment/custody and overlap still approval input; no stored raw private key or client secret.

Assertion: OAuth token request grant_type=client_credentials, client_id exact, client_assertion_type urn:ietf:params:oauth:client-assertion-type:jwt-bearer, client_assertion, resource exact URI and requested registered scope. iss=sub=client_id, aud exactly singleton configured token endpoint, iat/exp required, 0<exp-iat<=120s, iat<=now+30s, exp>now (no extra expiry leeway for assertion); jti unique and bounded. Verify signature, algorithm, key ownership/revision/effectiveness and all claim checks before reserve. Reject wrong audience/key/subject, expired, duplicate or malformed; same jti in different client scope isolated. Atomic durable unique (issuer identifier, tenant ID, client registration ID, SHA256(jti)); one winner across instances/restart. Scope not key ID: rotation cannot reset replay. Retain until exp+30s at minimum, delete expired rows bounded (candidate batch <=1000, at most once/minute, indexed expiry); purge clock uses DB clock and skew bound. On DB outage/uncertain commit deny; never erase reservation on downstream denial or signing failure. Rate-limit client authentication and bound assertion length <=8192 before parsing. No raw assertion, jti, token or private material in evidence. #546 tested 1/20 on disposable PG using (issuer,client,hash) and table outage; proposed tenant/registration binding and actual credential lifecycle require G3-04/05 tests, not already implemented. Race: current checks and conditional replay reserve, recheck exact registration/credential/tenant/subject/admission immediately before signing; no distributed linearizable revocation claim. Revocation commits independent of evaluator; no issue after observed revocation; previously minted JWT bounded by D3. No external calls inside authoritative transaction. Error neutral invalid_client/invalid_grant as appropriate, unavailable mandatory authority temporarily_unavailable, no leak.

### Catalog and exact admission (ARCH-G303-01/02/03/05/06)

- One Catalog-owned client authority across L0/R1. Use a compatible typed extension or migrated successor with one authoritative writer, not two registries. Global immutable client_id routes to exactly one stable registration/Tenant across profiles; never reuse retired IDs, infer Tenant from claims or silently rebind subject. Map existing ACTIVE/RETIRED exactly; proposed DRAFT -> ACTIVE <-> SUSPENDED -> RETIRED (also ACTIVE/DRAFT -> RETIRED), terminal RETIRED. Only explicit authorized activation after current complete binding/eligibility checks; unsupported grant/kind combinations disabled. PUBLIC_HUMAN supports current S256 code flow when explicitly registered; CONFIDENTIAL_SERVICE only proposed client_credentials after gated implementation; CONFIDENTIAL_HUMAN remains disabled until confidential proof+PKCE contract accepted. L0 clients retain IDs/revisions/subject semantics, redirects, scope vocabulary and behavior. No dual writers during migration.
- Keep authenticationTargetId (where Principal authenticates) distinct from resource-access ApplicationTarget (exact governed target) and ResourceRegistration (intended API audience). For initial service, require the explicitly bound eligible service Principal and exact target compatibility under the approved service binding; human authentication target need not equal resource-access target. Exact Tenant/parent Application/target relationships are current Catalog semantics. One client may have bounded multiple bindings; each binding exactly one resource and one tenant-local access target, at most one active binding for (Tenant, client, resource). Audience resolution is unique within configured issuer/environment: a shared audience is one explicit deployment-owned offering with tenant-specific admissions, never duplicate ambiguous tenant-owned registrations or nullable ownership. Domain/Data to choose extension vs separate Catalog aggregate and exact cardinality/indexes.
- Proposed R1 semantic admission request: trusted Tenant, Identity ID, authenticated Principal ID, exact active client registration and material revision, exact resource/binding ID and revision, resource-access ApplicationTarget ID, requested scope set, typed admission requirement, evaluation instant. Catalog resolves allowed resource/target/scope; Access returns ALLOW, DENY or UNAVAILABLE from current governed Role/Entitlement semantics and applicable Identity epoch, temporal validity, current Role expansion, SPECIFIC Principal compatibility and Catalog availability. The admission requirement must be explicitly configured as exact existing Entitlement(s) and/or Role-derived entitlement coverage for that target, not any entitlement in the Application, not JWT scope, and not a new assignment target. A required entitlement must resolve to the exact target; any/all semantics and concrete IDs require owner-approved registration policy. Missing/ambiguous required policy fails closed. Access owns current access queries and mutations; Governance owns mandatory policy and approval. Preserve ADR-0055 and 0059 for existing admission/reduction. No new privilege merely from client registration, token request or policy read. No provider calls inside authoritative transactions.
- Existing IdpApplicationAccessEvaluator.hasCurrentAccess(ApplicationId) is L0 application-level admission; do not reuse it unchanged as the sole R1 target proof. Required negative fixture: T1 subject with valid access to target A but no required access to target B of the same Application requests B; deny before token issue. Positive: exact current admission for B and valid binding allows only B. Wrong Principal/tenant, stale epoch, unavailable required authority, target retirement and multi-target Role/SPECIFIC incompatibility are negative cases. No partial read treated as absence or positive proof.
- Client/binding suspension/retirement suppresses only exact issuance; no generic GrantApplicationAccess, no broad revoke of other valid assignments, no Catalog writes to Access. ADR-0052 terminal target reduction remains exact, bounded, causally idempotent, current-state rechecked by Access. Temporary unavailability is non-destructive. If a future client-specific access cause is required, model it explicitly and separately accept its reduction policy; otherwise no assignment reduction on client retirement alone. Reductions do not await unrelated evaluator availability.

### Human R1 authorization code (ARCH-G303-04)

Proposed additive Platform-owned technical code extension, not an IAM business aggregate. At authorization, resolve a single registered resource (explicit request or unambiguous configured default), exact client/binding/current target and allowed scope intersection; check required current governed admission. Persist immutable profile R1, resource registration ID + exact audience URI, client-resource binding ID + material revision, resource-access target ID, exact admitted scope set, and existing registration ID/revision, Tenant, Application, session/subject/Principal/Credential anchor, redirect, S256 PKCE, time and nonce. Pin resource revision or material version as applicable; no raw code (digest only). The authorization request cannot select an arbitrary issuer/Tenant. L0 codes retain current representation/behavior; explicit profile controls decoding and issuance.

At token redemption resolve exact client and trusted Tenant, atomically consume original code once, then compare profile, original resource/audience, binding ID/revision and material target/scope context. If token request supplies resource, it must exactly match pinned resource; absent resource uses pinned resource, never a newly selected default. Revalidate exact current client/binding/resource/target, original session and subject/Principal/Credential/Tenant plus current target-specific Access admission; changed material revision or denial -> invalid_grant, mandatory unavailable -> temporarily_unavailable; no token, no code restoration, no L0 fallback, no session idle touch. Existing ADR-0066 consume and current-state guards apply. R1 access JWT audience is pinned resource; ID token aud remains client. Preserve original L0 profile and code handling. Required fixtures: authorize A then redeem B -> burn/deny; change binding revision, resource target, admission, scope or retire resource after authorize -> burn/deny; wrong Tenant never consumes; successful exact A exchange issues A and no B; expired/used code and same code concurrent exchange preserve one-use.

### Timing, verified scope and consumer authority (SEC-G303-01/03/04/05/06)

- R1 issuer stamps actual issuance time (no deliberate future dating; verifier future tolerance is not permission to advance iat). Max lifetime 300s, leeway 30s, measured relative drift <=5s; 335s JWT-only elapsed residual from actual issue conditional on clock health. Bound and measure final mandatory check-to-sign/response delay separately; no claim 335s from revocation when last issuance may occur later. Candidate 2s authority budget is end-to-end decision deadline, including dependency calls/retries; confirm allocations and measurement with Security/Platform/Storage before acceptance. Fail closed if mandatory current authority/trust unavailable or clock unhealthy; reductions remain independently available. Mandatory issuance evidence must be committed before token response under ADR-0070; failures do not reverse valid reduction.
- JWKS configured HTTPS only, monotonic refresh 30s/hard age 60s, single-flight plus per-issuer bounded refresh budget/cooldown/backoff (exact limits review/measurement pending), no unbounded sequential unknown-kid refresh, no stale/failed mandatory refresh fallback. Publish before issue, retain old public key candidate >=395s from last issue, emergency removal measured from observable authenticated publication with propagation uncertainty. Operational rotation/custody, refresh-abuse and clock tests required, not inferred from component CI.

## Bounded acceptance closure — SEC-G303-07 recovery-safe authorization

Status: proposed design requirement for owner/specialist acceptance; no implementation, schema, ADR promotion or production activation. Sources: [Security changed-head finding](https://github.com/wyrmgate/iam/pull/549#issuecomment-6911362787), ADR-0043, ADR-0051/0052/0055/0059/0063/0066/0070, production-readiness and production-recovery-drill. D1–D4 approved direction unchanged; additional owner nine-domain design remains a gate. RPO <=5m and RTO <=60m unchanged. Recovery is not permission to resurrect authority. A replay ledger fence alone does not prevent a NEW assertion using a credential restored ACTIVE after its post-backup compromise/revocation.

### Required re-entry safety (proposed)

1. Platform recovery starts a durable, fail-closed re-entry fence for every affected issuance/authorization path before a restored authority store is exposed. Fence scope is explicit deployment or known affected Tenant/resource/provider; if completeness/scope cannot be established, widen to the affected deployment/consumer, not a guessed narrow scope. Fence state and recovery generation must be independently recoverable or default closed on missing/untrusted state; never assume an old database's READY flag is current. Drain/fence old writers, workers and consumers; no split brain. Repeated recovery/restart or stale recovery generation cannot reopen a fence. Platform owns technical readiness only, not grants or lifecycle decisions. Allow separately authorized recovery/control and authoritative reduction paths; no privilege increase or normal protected effect with uncertain authority.
2. Establish the recovered checkpoint, trusted incident/recovery timeline, affected authority sources and completeness/watermarks. Recover authenticated authoritative changes after checkpoint when possible from owner-approved protected durable sources (WAL/PITR or complete owner-controlled recovery evidence with verified sequence/integrity). Audit evidence, projections, external provider observation and event fragments are not authority by themselves and cannot be directly applied as grants. Each owning capability validates/reconciles its own state through semantic commands and revision/causal idempotency. Preserve terminal revocation/compromise, exact retirement/reduction, subject/Principal eligibility and Tenant isolation; never infer valid authority from missing or partial records. No blanket reverse of an accepted reduction. If complete recovery is impossible, conservatively suspend/revoke/rotate affected bindings/credentials/grants or keep scope fenced, then independently re-establish eligibility via authorized owner decisions. No automatic restoration of ACTIVE from historical backup; no cross-domain DB writes.
3. Scope checklist: Tenancy lifecycle/isolation, Identity lifecycle/Principal/subject corrections, Catalog client/resource/binding/target retirement, Credential compromise/revoke/key version/rotation (including issuer signing keys, separate custody), Access exact assignment reductions and effective governed access, Governance mandatory current policy, Administration bindings/grants/recovery authorization, Integration current provider observation/reconciliation (not authority), Audit integrity/evidence. Storage independently fences/reconciles its own binding/membership/module/local grant/file/purpose/transfer and pending work state; never infer local grant from IAM token/scope. No shared database or centralized recovery grant writer. Platform technical replay/code/session/token/worker state must be recovered or invalidated/fenced; lost single-use reservation window and revoked authority are separate conditions. If a credential was exposed/compromised or trust version uncertain, rotate/withdraw under actual owner policy before acceptance; wait for verified verifier refresh/withdrawal, fence affected consumers and invalidate or drain pre-recovery tokens/handles as necessary. Existing self-contained bearer expiry is not a substitute for local current-authority re-entry. No service bytes while recovery or D3 transport proof incomplete.
4. Release each fence only after required authoritative owner evidence is current, complete for its exact scope/recovery generation, signed/authorized as appropriate and reconciled with the consumer's recovery generation. Record recovery checkpoint/generation, owner decision/reference, verification/watermark and outcomes without raw tokens/key material. Independent Security/QA verification, Platform operator and accountable product/technical owner acceptance; absence/unavailability or stale evidence keeps scope closed. A repeated restore reopens the fence; do not carry positive readiness across generations. Denied or uncertain actions do not create effects. Recover/replay idempotently with current authorization before retry; no distributed rollback. RTO measurement ends only when applicable re-entry criteria pass; degraded/fenced mode is visible and counts against applicable service objectives, not falsely READY. Do not promise lossless recovery or RTO compliance without measured drill.

### Acceptance scenarios and decision
