# ADR-0064: Bounded first-party authentication and local password change

Status: Accepted

## Context
Credential v3 (#513) keeps the five credential kinds as metadata and separates lifecycle, process and provider fulfillment. First-party password verification currently enumerates all effective password metadata and the proof lacks an explicit tenant. Installation enrollment is the only concrete local verifier creation path. A general external secret manager or provider rotation engine is not required to support routine first-party password change.

## Decision
- Bound first-party password lookup to eight effective candidates plus one overflow sentinel, deterministic ordering. Overflow fails closed without selecting an arbitrary subset or exposing the count. Reject empty passwords and keep private copies cleared. This is an authentication work bound, not a general credential cardinality cap. No new external verifier provider is enabled.
- Verification proof carries trusted tenant ID, Principal ID, Credential ID and revision. Session establishment must reject mismatched tenant/Principal and revalidate current Identity/Principal eligibility and exact Credential revision/effectiveness. Every session resolution continues current-state revalidation. A stale proof cannot create valid authority; races after checks are fenced by session resolution.
- First concrete rotation execution is a self-service change of an existing effective local PASSWORD authenticator. It is not recovery, reset, administrative impersonation, external provider rotation, or generic enrollment. The caller proves current password for the exact authenticator of a current first-party browser session; tenant, subject and credential come from server state. Require the established same-origin CSRF boundary. No client-supplied tenant/Principal/credential ID.
- New password must be distinct from current, 15–1024 characters, with no composition rules. Current password must be nonempty (existing installation credentials retain compatibility). Ambiguous effective local authenticators fail closed; no automatic recovery. Local verifier material is salted one-way, never returned, and transactionally co-located with Credential authority. A single bounded local transaction locks the old Credential, rechecks revision, verifies the eligible subject, creates a new distinct verifier/reference and Credential, records a completed CredentialRotation, revokes the old Credential and preserves history. No external call, distribution task, generic BPM or synthetic provider evidence. Local cutover is atomic, with zero committed overlap; intermediate steps need not be externally visible. Existing open routine rotation blocks this path. No new Credential is created for an ineligible subject or stale old proof. The old Credential's prior validity end is preserved, not silently extended. Subsequent login uses the new password; exact old-revision sessions fail revalidation. Old verifier history is not an active authenticator.
- Duplicate execution is fenced by the exact old Credential revision and revocation; a retry after commit cannot create another replacement using the old credential. On an uncertain response the caller signs in with the new password; do not store password-derived request fingerprints, raw secrets or replayable proof. A separate recovery/reset design is deferred.
- Dedicated authentication/change input may accept presented passwords over protected transport; no ordinary Credential resource API gains secret input or output. Audit records only semantic operation/actor/target/correlation/outcome after the transaction. Existing metadata-only administrative rotate remains a plan, not execution evidence. No arbitrary status mutation.
- External rotation, CredentialBinding, automated rotation policy, MFA, password recovery and confidential SSO client secrets remain deferred until concrete contracts are accepted.

## Consequences
No new aggregate or migration is required for the local atomic path. The dedicated local adapter must share the Credential transaction; an external adapter cannot be substituted into this atomic path. The first slice implements bounded proof/session fencing; a subsequent slice implements the local password change operation and its API/security tests. Neither claims external provider acceptance.
