# ADR-0070: Bounded first-party authentication runtime and security evidence

Status: Accepted

## Decision

- Shared Platform technical admission counters bound credential verification to 120 attempts per Tenant per minute and ten attempts per known Principal per five minutes, and new login interactions to 120 per Tenant per minute. PostgreSQL atomic fixed-window admission uses database time, existing trusted stable IDs only (never usernames, password or IP). Unknown client/invalid envelope is rejected before credential verification; unknown subject consumes Tenant budget. Saturation is a generic denial, not account enumeration; no authoritative account lockout. Counts include successes. A saturated principal/tenant can deny legitimate sign-in until the window resets, an explicit baseline trade-off. Deployment ingress rate limiting remains needed for volumetric attacks and a global tenant-wide denial-of-service risk.
- Mandatory governed-access evaluation is bounded to 10 pages of 200 entitlements; positive proof may short-circuit, complete absence denies, overflow/non-progress/evaluator failure is unavailable and no token/code issues. Do not treat a partial result as absence. Entitlements must also have an active target and parent Application. This is a temporary bounded implementation; a future optimized Access-owned application existence query can supersede it.
- Audit receives typed action/outcome, trusted Tenant and verified actor only when authenticated, stable client/session/code IDs and correlation/causation. No login name, raw protocol state, redirect, hashes, passwords, tokens or assertion material. Mandatory success evidence must be committed before returning a new session/code/token; if unavailable fail closed and revoke unexposed new session where necessary. Failed/denied admitted authentication attempts and actual session revocation are best-effort evidence; Audit failure never prevents privilege reduction. Do not append unbounded anonymous attack/replay events: unknown clients, invalid envelopes and saturated admission are operational telemetry only. No new public audit event schema.
- Platform cleanup deletes expired interactions, expired/consumed codes after one hour, and revoked/expired sessions after 24 hours, only after referencing codes are removed. Expired rate counters after 24 hours. Bounded ordered batches of 200 per class per minute, SKIP LOCKED, no cascades or Audit deletion. Cutoffs use database time; cleanup cannot renew or reactivate anything. Audit evidence retention follows Audit-owned legal hold/retention independently. No asynchronous secret payload.
- Tighten raw token parsing to canonical 43-character base64url; public JWKS requires exact current public key material/algorithm, not just matching key ID; signing verifies the emitted signature against the selected published key before releasing JWTs. Private key material remains in provider. Profile/email scope metadata stays reserved for compatibility; current claims remain explicitly minimal and discovery/contract must not claim implemented profile/email claim release. No raw secrets in diagnostic records.

## Consequences

New V33 runtime counter/cleanup indexes only; no change to authoritative access or identities. Limits and retention are implementation baseline values; scaling/production acceptance must measure saturation, latency, cleanup throughput and Audit availability. No retroactive JWT revocation or concrete upstream provider activation.
