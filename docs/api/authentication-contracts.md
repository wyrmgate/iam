# Authentication / IdP / SSO Contracts

## Scope

This document defines the first public control-plane resource contracts for the Authentication capability established by ADR-0042. It does not redefine the standards-defined OIDC protocol endpoints; those are exposed by the Authentication protocol adapter and must remain conformant to the implemented OIDC/OAuth profile.

All administrative routes are same control-plane security model as other `/api/v1/**` resources: authenticated governed actor, Administration-owned permission evaluation, tenant isolation, semantic errors, correlation IDs, optimistic revision and causal idempotency for retryable mutations.

## Administrative resources

### AuthenticationClient

`AuthenticationClient` is an Authentication-owned tenant-bound OIDC/OAuth relying-party registration.

Initial fields:

- `id` — stable server-generated resource ID.
- `clientId` — immutable protocol client identifier generated by the server unless a future contract explicitly allows an operator-supplied identifier.
- `displayName` — governed operator-facing name.
- `clientType` — `PUBLIC` or `CONFIDENTIAL`.
- `redirectUris` — non-empty exact HTTPS callback URIs; loopback HTTP may be permitted only by an explicit development/native-client policy.
- `postLogoutRedirectUris` — exact registered logout callbacks.
- `grantTypes` — first slice permits only `AUTHORIZATION_CODE`; refresh-token support is added only when its runtime/storage semantics are active.
- `scopes` — allow-listed protocol scopes. `openid` is required for OIDC clients.
- `state` — `ACTIVE` or `DISABLED`.
- `revision` — optimistic resource revision.
- `createdAt`, `updatedAt`.

Client-secret/private credential values are never included in this resource. A later confidential-client credential operation may accept write-only secret input/reference but ordinary GET/list remains redacted.

Permissions:

- read/list: `authentication-client:read`
- create: `authentication-client:create`
- update: `authentication-client:update`
- disable: `authentication-client:disable`

Routes:

- `GET /api/v1/authentication/clients`
- `POST /api/v1/authentication/clients`
- `GET /api/v1/authentication/clients/{clientId}`
- `PATCH /api/v1/authentication/clients/{clientId}`
- `POST /api/v1/authentication/clients/{clientId}/disable`

Create and disable require `Idempotency-Key`. PATCH/disable require `If-Match` and return a new `ETag` on success. Collections use deterministic integrity-protected cursor pagination.

### AuthenticationLoginBinding

`AuthenticationLoginBinding` maps one tenant-local normalized login identifier to an existing governed Principal and Identity. It is Authentication state, not a duplicate user record.

Fields:

- `id`
- `loginIdentifier` — display form, data-classification controlled.
- `normalizedLoginIdentifier` — never accepted as caller authority; derived server-side and not required in ordinary responses.
- `principalId`
- `identityId`
- `state` — `ACTIVE` or `DISABLED`
- `revision`
- `createdAt`, `updatedAt`

The referenced Principal/Identity must belong to the same tenant and be compatible with interactive authentication policy. Binding creation does not create or mutate Identity/Principal/Credential.

Permissions:

- read/list: `authentication-login-binding:read`
- create: `authentication-login-binding:create`
- update: `authentication-login-binding:update`
- disable: `authentication-login-binding:disable`

Routes:

- `GET /api/v1/authentication/login-bindings`
- `POST /api/v1/authentication/login-bindings`
- `GET /api/v1/authentication/login-bindings/{bindingId}`
- `PATCH /api/v1/authentication/login-bindings/{bindingId}`
- `POST /api/v1/authentication/login-bindings/{bindingId}/disable`

### AuthenticationSession

Browser/SSO session resources are read/revoke only through administration. The resource exposes metadata, never the bearer session identifier/cookie value.

Fields may include:

- `id` — non-bearer administrative resource identifier distinct from the session secret;
- `identityId`, `principalId`;
- `clientId` when established for an OIDC interaction;
- `assuranceLevel`;
- `authenticatedAt`, `lastSeenAt`, `expiresAt`;
- `state` — `ACTIVE`, `REVOKED`, `EXPIRED`.

Permissions:

- read/list: `authentication-session:read`
- revoke: `authentication-session:revoke`

Routes:

- `GET /api/v1/authentication/sessions`
- `GET /api/v1/authentication/sessions/{sessionId}`
- `POST /api/v1/authentication/sessions/{sessionId}/revoke`

Revocation requires `Idempotency-Key` and `If-Match` where the current session revision is exposed.

## First-party browser login surface

Interactive login is not an administrative CRUD API and does not accept an Administration actor header/context.

The browser flow is same-origin and session-oriented:

1. an OIDC authorization request identifies a registered tenant-bound client and exact redirect URI;
2. if no eligible Authentication session exists, Wyrmgate renders/serves a login surface;
3. login identifier resolution returns no enumeration-sensitive distinction;
4. Authentication delegates presented authenticator verification to Credential;
5. successful authentication creates/rotates an HttpOnly secure session and resumes the pending OIDC authorization request;
6. authorization code is issued once and exchanged with the original PKCE verifier;
7. token issuance re-checks client/session/subject eligibility required by policy.

Bearer/refresh/session secrets are not persisted in browser localStorage/sessionStorage.

## OIDC protocol endpoints

The initial adapter must expose standards-compatible equivalents of:

- issuer discovery: `/.well-known/openid-configuration`
- public signing keys: JWKS URI advertised by discovery
- authorization endpoint
- token endpoint
- end-session/logout endpoint when activated

Exact endpoint paths are part of the protocol adapter contract and discovery metadata; control-plane clients must not hard-code them from administrative resource paths.

## Claims

Initial OIDC ID tokens expose only protocol-required/minimal claims plus explicit allow-listed claims. `sub` is Authentication-owned opaque subject identity. Tenant context is explicit and data-minimized. Wyrmgate Administration permission sets, AdministrativeRoles/Grants and arbitrary Identity attributes are not emitted merely because they exist.

## Errors

Administrative APIs use existing Wyrmgate semantic HTTP errors including `401`, `403`, `404`, `409`, `412`, and `503` as applicable. OIDC protocol endpoints use standards-compatible protocol errors without leaking internal credential/provider detail.

## Explicit non-goals of the first slice

- SAML IdP endpoints;
- implicit grant;
- Resource Owner Password Credentials grant;
- dynamic client registration;
- arbitrary custom-claim scripting;
- automatic mapping of external groups/scopes to Wyrmgate permissions;
- treating Catalog Application or AccessAssignment as the OIDC client aggregate;
- exposing raw Credential/secret material.
