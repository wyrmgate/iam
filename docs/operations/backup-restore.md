# Backup and Restore

## Scope

Sprint 13 establishes the first PostgreSQL backup/restore and recovery baseline for Wyrmgate IAM. It protects authoritative relational state from operator mistakes and failed changes without coupling recovery to application rollback.

This is an operations implementation contract, not a new IAM domain model. The canonical distinction between authoritative state, observations, evidence, and projections remains unchanged.

## Recovery principles

- Application rollback and database restore are separate operations.
- Normal deployment rollback never performs a database down-migration or automatic restore.
- Backups are created with PostgreSQL `pg_dump` custom format from the running database. `pg_dump` provides a transactionally consistent logical snapshot without stopping the IAM server.
- A backup is published only after it is non-empty and `pg_restore --list` can read it.
- Every published archive has a SHA-256 sidecar. Restore requires that checksum to validate.
- Restore is destructive and operator-driven. It requires an explicit `IAM_RESTORE_CONFIRM=RESTORE:<profile>` guard.
- Before a destructive restore, the restore script creates a fresh safety backup of the current database unless the operator explicitly invokes the emergency skip escape hatch.
- Restore stops the IAM server before replacing the database, restores the archive, runs current Flyway migrations in one-shot migration mode, and only then starts the server again.
- If restore or migration fails, the IAM server remains stopped for investigation rather than serving an uncertain database state.

## Backup locations

Host provisioning reserves:

`/var/backups/wyrmgate/iam`

Scheduled backups use a profile-specific child directory, for example:

`/var/backups/wyrmgate/iam/dev`

Backup names use UTC timestamps:

`dev-YYYYMMDDTHHMMSSZ.dump`

The checksum is stored beside the archive as:

`dev-YYYYMMDDTHHMMSSZ.dump.sha256`

Backup files and checksum files are mode `0600`. The directory is mode `0700` when created by the backup script.

Backups must remain outside `/opt/wyrmgate/iam/releases`; a release directory is disposable application material and is not a backup archive.

## Manual backup

On a DEV host with a healthy current release:

```bash
sudo /opt/wyrmgate/iam/current/deploy/scripts/backup-postgres.sh \
  dev \
  /opt/wyrmgate/iam/current \
  /var/backups/wyrmgate/iam/dev \
  14
```

The last argument is retention in days. Retention deletes only Wyrmgate backup archives/checksum sidecars matching the selected profile.

DEMO uses the same script with profile `demo` and its own release/backup paths if an operator intentionally wants a snapshot. Public DEMO is reset-oriented and does not require scheduled backups by default.

## Scheduled backup

The Ansible host role installs `wyrmgate-iam-backup.service` and `wyrmgate-iam-backup.timer`. Scheduling is opt-in so generic IAM hosts are not accidentally assigned the wrong environment profile.

Relevant variables:

```yaml
wyrmgate_backup_enabled: true
wyrmgate_backup_profile: dev
wyrmgate_backup_retention_days: 14
wyrmgate_backup_calendar: '*-*-* 02:15:00'
wyrmgate_backup_randomized_delay_seconds: 900
```

When enabled, the timer is persistent. If the host was powered off at the scheduled time, systemd runs the missed job after startup. A randomized delay avoids every small deployment starting I/O at exactly the same instant.

The service has a `ConditionPathExists` guard for the current release backup script, so host provisioning can safely occur before the first application deployment.

## Restore

Only restore backups generated by a trusted Wyrmgate environment. PostgreSQL restore archives can contain database objects that execute code during restore; do not restore arbitrary or untrusted archives.

Example DEV restore:

```bash
sudo IAM_RESTORE_CONFIRM=RESTORE:dev \
  /opt/wyrmgate/iam/current/deploy/scripts/restore-postgres.sh \
  dev \
  /opt/wyrmgate/iam/current \
  /var/backups/wyrmgate/iam/dev/dev-YYYYMMDDTHHMMSSZ.dump
```

The restore script performs these steps:

1. validates the archive checksum;
2. starts/waits for PostgreSQL if necessary;
3. validates that `pg_restore` can read the archive;
4. creates a fresh pre-restore safety backup;
5. stops the IAM server;
6. drops and recreates the configured IAM database;
7. restores the archive with owner/ACL portability flags;
8. runs the current server image in migration-only mode so the restored database reaches the current schema;
9. starts the IAM server and waits for its container health check.

After the script succeeds, verify the public health endpoint and application-level recovery checks before normal traffic or administrative work resumes.

`IAM_RESTORE_SAFETY_BACKUP_DIR` may override the default safety directory (`/var/backups/wyrmgate/iam/<profile>/pre-restore`). `IAM_RESTORE_SKIP_SAFETY_BACKUP=true` is an emergency-only escape hatch and should not be used during routine recovery.

## What is backed up

Sprint 13 covers PostgreSQL logical state. That includes the IAM relational database and Flyway schema history stored inside it.

It does not yet back up:

- Caddy certificate/configuration volumes;
- host operating-system state;
- container images, which are immutable and retained in GHCR rather than backed up from hosts;
- external provider state;
- observability backend data;
- secrets/signing keys, which require their own protected recovery procedures;
- off-host or cross-region copies.

## Recovery objectives and DR limits

This sprint does not declare production RPO/RTO, high availability, point-in-time recovery, or disaster recovery. A daily local logical backup is a low-cost recovery layer, not protection from total host/disk loss.

Before production readiness, operations must define environment-specific RPO/RTO and add at least:

- encrypted off-host backup replication;
- protected recovery of secrets and signing keys;
- periodic automated restore drills;
- backup age/failure monitoring and alerting;
- capacity/retention policy based on real database growth;
- production-appropriate PostgreSQL HA/PITR where justified;
- documented host/regional disaster-recovery procedures.

## Verification

CI exercises the backup path against PostgreSQL 18, verifies the SHA-256 sidecar, restores the resulting archive into a second database, and checks seeded data. CI also guards the destructive restore confirmation, safety-backup, server-stop, and migration-only contracts.

A live environment still requires an operator restore drill. A backup is not considered operationally proven merely because `pg_dump` exited successfully.
